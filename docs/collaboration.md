# 团队协作流程

MergeLane 面向一个团队里的多位成员：每人使用自己的 Agent 客户端与个人凭据，通过共同的任务平台协调工作。共享内容包括任务说明、负责人、前置依赖、任务状态和进度记录。

## 团队先约定什么

1. 选择已有的受支持任务平台，每位成员确认自己能访问相应仓库或项目。
2. 每人在开发机安装 MergeLane，并从 [文档目录](README.md) 选择相应平台的接入文档配置自己的 MCP 客户端。
3. 确定负责人、参与成员和代码协作方式。成员可以各用独立克隆、分支或 worktree；代码评审和合并沿用团队的 PR 与 CI 流程。
4. 约定何时更新任务状态、何时发布进度。任务状态在各自平台中维护，MergeLane 查询该状态；进度说明、验证结果和下一步通过检查点评论共享。

Gitea／GitHub 用账号用户名，Plane 使用成员 UUID，GitLab 使用数字用户 ID，Jira 使用 accountId，Agent 从上下文的成员列表中解析成员身份。任务同名或成员重名时，应先确认具体对象。

## 先录入，再分配

1. 录入人对自己的 Agent 说“建一张标题为‘账单导出异常’的 Issue，先留空负责人”。Agent 经确认调用 `*_create_issue`，返回工单链接。配置了默认项目后，标题是唯一必填内容，描述可选。也可以传 `project` 指定本次的目标项目。
2. 把链接交给管理者。管理者可以说“把这张 Issue 分给 Bob”。管理者的 Agent 经确认调用 `*_assign_issue`，传入 `issue` 链接和该平台的 `assignee` ID。若该工单已由同一人负责，会直接返回已指派的工单；若已有其他负责人，工具会报错。

两次写入由各自的账号执行，均需启用对应平台的写入工具。MCP 调用方通过 `confirmed: true` 传递用户确认。这两个工具可以直接调用。同一张工单交给一位管理者指派，因为读取负责人和写入指派是两次平台请求。如果建单请求的结果不明确，先在目标项目查询，避免重复建单。

Plane 建单使用配置的工作空间，项目需关闭默认指派。Jira 站点需允许未指派工单，所选工单类型须允许仅凭标题创建。[Plane 项目配置](https://developers.plane.so/api-reference/project/update-project-detail) · [Jira 未指派工单设置](https://support.atlassian.com/jira/kb/unable-to-change-the-default-assignee-field/)

## 编辑工单

贴上已有工单的链接，并告诉 Agent 要修改的标题或描述。审阅改动后，Agent 调用对应平台的 `*_edit_issue`。工具需要平台写入开关、账号编辑权限和 `confirmed: true`，返回工单链接及编辑后的内容。

```json
{"issue":"team/web#42","title":"修复账单导出异常","confirmed":true}
```

这组参数适用于 Gitea 和 GitHub。至少提供 `title` 或 `description` 之一。省略字段会保留原值，提供 `description` 会替换整段描述，传入空字符串可清空描述内容。描述中用于恢复计划的 MergeLane 标记会自动保留。Plane 和 Jira 将新描述作为纯文本写入各自的富文本格式。

## 从一个目标开始

例如团队要做“账单导出”，Alice 实现导出接口，Bob 开发下载入口，负责人跟踪总任务。

| 阶段 | 成员对自己的 Agent 说什么 | 团队里可见的结果 |
| --- | --- | --- |
| 明确需求 | “读取账单导出总任务，列出验收条件。” | Agent 读取现有工单、成员与前置条件 |
| 制定分工 | “拆成接口和下载入口，分别交给 Alice 和 Bob。下载入口依赖接口。先给我看计划。” | 当前会话内的计划预览，远端尚未创建任务 |
| 发布计划 | 审阅标题、负责人、验收条件和依赖后确认发布 | 远端子任务、负责人、原生阻塞关系和总任务汇总 |
| 开展工作 | “查询分给我的账单导出任务，读取依赖，领取后开始。” | 各自推进分到的任务，本机同一张工单只有一个会话能领取 |
| 共享进展 | “记录接口已完成、测试结果和待评审事项，先给我看内容。” | 确认后发布工单评论，其他成员下次查询即可读取 |
| 查询状态 | “账单导出目前谁在做，哪些任务被阻塞，最近验证结果是什么？” | Agent 搜索任务并读取上下文，汇总当前状态和评论 |

前置依赖可以表示顺序约束。若前后端需要并行推进，可先把接口约定拆成独立任务，让实现和消费方依赖已确认的约定；任务如何拆分由团队确认。

每位成员都可以持续查询和发布自己有权限的工作进展。换人、暂停或切换 Agent 会话时，同一套检查点也可用于接续上下文。

## 本地任务租约

任务平台继续保存负责人和任务状态。MergeLane 的本地租约记录当前占用任务的执行会话，覆盖同一台电脑、同一个系统用户下的客户端和 worktree。团队成员之间仍按任务平台的分派协调。

1. Agent 先查任务与依赖，准备实际开工时调用 `mergelane_claim_task`，传平台名和工单链接或该平台支持的简写。已有会话持有时领取失败，应停止开工。只查进度时可调用 `mergelane_task_lease`。
2. 领取成功后，执行会话保留返回的 `lease_id`。同一 MCP 连接自动续租，默认每 40 秒续到 120 秒。需要发布检查点时，在对应平台的 `*_checkpoint` 中带上这个 ID 并确认内容。
3. 完成或暂停时，先保存所需检查点，再调用 `mergelane_release_task`。发起连接退出或崩溃后续租停止，其他会话在最后一次租约过期后可以重新领取。接管生成新 ID，旧 ID 无法续租、释放或发布检查点。

有些宿主会让多个聊天共享一条 MCP 连接，MergeLane 无法单独感知某个聊天是否已停止。自动续租在领取、续租工具调用或持有者尝试发布检查点之后最多继续一小时。长时间工作且没有检查点时，Agent 可以调用 `mergelane_renew_task` 报告仍在工作。

保护范围是同一台电脑上通过 MergeLane 协调的执行与检查点。本地租约无法约束其他电脑、直接修改文件或直接调用任务平台的操作。曾在本机领取过的工单，再通过 MergeLane 发布检查点时必须持有有效租约，即使上一次租约已过期或已释放。

## 两种依赖

**任务依赖**表示哪项工作阻塞另一项工作，由对应任务平台的原生关系保存，受平台版本、套餐和权限限制。队员开始前读取前置任务，管理者据此查看阻塞原因。

**资料依赖**表示这项工作依据哪个版本的规范、样例或接口文件。在工单描述中使用 Gitea 文件的完整提交链接，MergeLane 将基线和默认分支上的文件内容比较，返回 `current`、`needs_review` 或 `unavailable`。更新基线前先完成适配和验证，再修改工单里的链接。

Plane 单独配置即可共享任务、分工、依赖和进度。需要检查 Gitea 文件版本时，再同时配置 Gitea 凭据。

## 保持信息可用

- 开始或提交工作前，让 Agent 重新读取任务上下文，核对负责人、验收条件、前置任务和资料版本。
- 在完成一个阶段、发现阻塞或完成验证时发布检查点。写清“完成了什么、验证了什么、还差什么”，并可附已经推送的提交链接。
- 管理者先搜索，再读取命中任务的上下文。搜索摘要反映任务状态和负责人，具体进展由上下文中的评论和检查点补充。
- 团队同时改动代码时，使用各自的工作区和分支，完成评审与 CI 后再合并。
- 各客户端需要在查询时获取最新远端状态。`gitea-watch` 可轮询选定的 Gitea 工单并输出变化；MCP 本身不向所有客户端广播实时更新。

## 计划变更与失败恢复

一次计划由一位负责人发布。部分请求失败时，先检查远端已保存的任务，再按原计划重试。换会话后先预览原样计划，再继续发布。在任务平台直接编辑工单描述时，请保留计划恢复标记。

已发布任务的标题与描述可以通过 `*_edit_issue` 修改。重新预览变更后的计划会生成不同的计划 ID，再发布会按新计划创建任务。
